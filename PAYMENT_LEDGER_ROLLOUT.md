# JobCrest: payment ledger and browser source

This release is staged. Installing the migration does **not** switch financial authority or contact Square. The legacy UI path remains available until an explicit server-side activation. No HTML template, CSS, or customer PDF layout is changed.

## Rehearse before any live switch

1. Install the migration on a staging copy and deploy the matching client/server there. Run `npm run check:go-live`. It runs the local admin/rep browser workflow twice: once with legacy payments and once with an activated disposable ledger. Use `npm run test:workflow:ledger` to repeat just the latter.
2. Check a verified backup and restore it in an isolated database. Back up the whole workspace, not only the job JSON. The payment and refund tables and all state rows are required to rebuild an activated ledger. Raw Square operational tables stay server-only.
3. In a trusted **server** environment, run `node scripts/prepare-payment-ledger.js`. It reads the configured workspace's bound estimates and verifies individual receipts from Square. It does not write by default. Give it SUPABASE_URL, the server key, the correct SUPABASE_STATE_ID, SQUARE_ENVIRONMENT, SQUARE_MERCHANT_ID and SQUARE_ACCESS_TOKEN from the server secret store. Never put keys in the browser or in source control. Test a Square sandbox invoice with multiple receipts and a refund before production.
4. Only for an authorized cutover, deploy matching code first, finish active edits, refresh open tabs, then run the same script with `--activate YYYY-MM-DD BACKUP_MD5 COLLECTED_DECIMAL` from the approved rehearsal. The server re-reads all linked Square invoices (GET only). Under a write lock the database compares the reviewed backup to live records, requires exactly the same balances before and after for every job (deleted jobs included), and refuses a stale rehearsal. No migration automatically activates the ledger. Activation reconciles the old ledger, historical invoice bindings, per-job Square amounts and company collected total inside a single transaction. A mismatch aborts the transaction. Do not substitute invented capture IDs or bypass the checks. Run `select public.crm_payments_reconciliation(), public.crm_ledger_totals();` in the trusted database session. Compare the three CRM money screens in an admin browser. If activation responded ambiguously, read the marker before retrying.
5. Do not revert to a JSON-writing client after activating. Once a payment has been written under the new model, use a forward fix or a coordinated database-and-application recovery with reconciliation. A previously deleted legacy job with payments must have its money reconciled before restoration; clearing its legacy payments is not a supported shortcut.

Manual entries are admin-only and use an idempotent create and version-checked edits/deletes. Net invoice payments now count towards the job balance. A refund that uncovers a balance reopens a Paid job. Square tenders are read-only to staff. Unsupported or unverifiable Square payments stay queued for review rather than being guessed.

## Editing the browser client

`src/crm/manifest.json` lists 14 feature source files in load order. Edit those sources, then run `npm run build:client` and commit the sources and generated `app.js` together. The release gate rejects a stale bundle. Production still fetches one classic script, without a bundler dependency or a new network waterfall. The three production, workflow and conversation add-ons call named hooks; they can no longer replace core functions at runtime. The source files still share the classic script's scope; this is not a rewrite to ES modules.
